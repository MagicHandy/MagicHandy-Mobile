# MagicHandy Mobile implementation review

*Links into `build/` open verification artifacts in a local checkout. Public Android downloads are on the [releases page](https://github.com/MagicHandy/MagicHandy-Mobile/releases).*

November 27, 2026 · Android v0.1.6 through v0.1.8 · reviewed commit `3abba0d`

**I would treat the voice-to-motion Stop race as a release blocker.** In a deterministic test, the footer Stop took a simulated Handy from Playing to Idle. A “Start motion” transcription from the listening session that Stop had just ended then went through the ordinary chat handler. The canned model replied, the same Handy returned to Playing, and its transport recorded one new motion batch. There was no second tap or new utterance. This is evidence about the app's command path.

## Findings in the releases since v0.1.6

### P1 · Speech recorded before Stop can start a new run afterward

The controller compares its listening session against `AppState.stopEpoch`. The motion engine advances its authoritative epoch immediately, but another coroutine publishes it to `AppState`. During that interval, the controller accepts an old transcript and dispatches an ordinary `SendMessage`. The core stamps the message with the **new** engine epoch. Its later checks therefore admit the message. I reproduced both the saved user message and the subsequent restart of the simulated Handy. The existing epoch test drains the scheduler before it checks the result, which skips this interval. Carry the original epoch into the core and check it there before saving, invoking a provider, or admitting motion. A regression should deliver a waiting transcript between the actual Stop and its UI publication. [Voice admission](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/voice/VoiceController.kt#L351) · [Core dispatch](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/core/src/main/kotlin/com/magichandy/mobile/core/session/MobileSession.kt#L360) · [Epoch publication](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/core/src/main/kotlin/com/magichandy/mobile/core/session/MobileSession.kt#L166)

### P1 · Download completion can start the microphone after Stop or a download-only choice

I reproduced two routes to a microphone-service start with an intercepted Android service launcher. First, I pressed Stop while **Download and start** was pending. The epoch advanced, the download completed, and the controller requested the microphone service. Second, I selected a Settings download with `andStart = false`, made it fail, and tapped **Retry** with microphone permission already granted. This also requested the service. The completion flag survives Stop while no listening session exists, and Retry reconstructs the flag from “no installed model and app visible.” Give the explicit start request its own cancellable identity, revoke it on Stop, and preserve the user's choice across retries. Both downloads should still be able to finish normally. [Settings download action](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/ui/voice/VoiceSheets.kt#L229) · [Retry](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/voice/VoiceController.kt#L181) · [Completion](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/voice/VoiceController.kt#L573)

### P2 · Bluetooth accepts missing evidence for commands that define a result

The v0.1.7 fix correctly accepts an ID-only reply to StopCurrentMode (RPC 715). The same exception now applies to every command. I used the production Bluetooth session with an in-memory peer that returned only the matching request ID for stroke limits, HSP setup, append and play. The app issued all four and reported **Playing**. The manufacturer defines response fields for those four methods. Keep the 715 exception and require the expected response for result-bearing commands, validating the playback state where relevant. This test isolates how the app handles missing evidence. The owner’s successful Original Handy connection remains valid. [Acknowledgement rule](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/transport/src/main/kotlin/com/magichandy/mobile/transport/handy/HandyCodec.kt#L144) · [Bluetooth command result](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/transport/src/main/kotlin/com/magichandy/mobile/transport/handy/HandyBluetoothSession.kt#L227) · [Manufacturer's pinned RPC schema](https://gitlab.com/sweettechas/platform/handy-public-rpc/-/raw/2398008c10d5f43903ec150e654968501f0ebc83/public/proto/handy_rpc.proto)

### P2 · Pausing and immediately resuming a model download can corrupt the finished file

Leaving the app cancels the download and immediately drops its job reference. Returning can start another writer while the first is still blocked in a read. With two correct local responses for a six-byte fixture, the resumed download returned success and renamed an **eight-byte** file. The digest had covered six logical bytes while both writers contributed bytes to the same file. The store's own size check then rejected the finished file. For a user this can waste a 671 MB or 2.6 GB download. Cancel the active network call, wait for its writer to close before resuming, and verify the installed file before marking it ready. [Pause](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/voice/VoiceController.kt#L132) · [Starting another writer](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/voice/VoiceController.kt#L505) · [Checksum and rename](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/voice/ModelStore.kt#L175)

### P2 · The 15-minute microphone timeout never expires while motion is paused

With a simulated Handy paused, Autopilot off and no speech, I advanced the clock by 16 minutes. The controller still showed listening. It counts every non-idle run as playing, so every tick resets the quiet clock even in `RunPhase.Paused`. Drive the timeout from actual playing or edging, and test paused and held states against the published promise. [Idle timer](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/voice/VoiceController.kt#L432) · [Playing predicate](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/voice/VoiceController.kt#L672) · [Release wording](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/docs/releases/v0.1.8.md#L8)

### P2 · Speech and spoken-Stop checks can delay each other

Both jobs use one synchronous recognizer. It always takes the latest Stop check ahead of a completed turn. With the shipping scheduler, 60 seconds of synthetic continuous speech and a **simulated 600 ms decode time**, the worker ran 99 checks, decoded zero whole turns and retained three 20-second turns. Conversely, once it starts decoding a whole turn, the next Stop check must wait for that call to return. The latest tail replaces its predecessor, while whole utterances and short sounds have no queue limit. Bound retained audio, give completed turns a processing budget, and measure end-to-end spoken-Stop latency while a long turn is already decoding. Device-specific recognition times remain an open measurement. [Queue selection](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/voice/RecognizerQueue.kt#L72) · [Synchronous recognition](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/voice/VoiceSession.kt#L173) · [Stop-check cadence](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/voice/SpokenStopWatch.kt#L37)

## Findings in the wider app

### P2 · An unsent draft follows the user into a different conversation

On an isolated Android emulator I opened a chat named `ReviewAlpha`, typed `DraftForAlphaOnly`, dismissed the keyboard, and selected **Chats → New chat**. The new conversation showed the old draft. Pressing **Send** saved it in the new conversation. Reopening the original confirmed it had never received the message. The composer remembers its draft and pending submission by composition position, and the navigation state is keyed by the Chat route. Scope them to the conversation ID and preserve separate drafts if returning to an earlier conversation should restore them. [Composer state](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/ui/chat/Deck.kt#L298) · [Route state](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/ui/MagicHandyRoot.kt#L299)

### P2 · Older chat messages are stored but have no path back to the screen

I saved 520 entries in the production Room store and reopened the chat. The first row was still in SQLite. The app exposed only the latest 513, starting at the eighth entry. `loadPage` always requests the newest window, and scrolling to the top offers no cursor for an earlier page. Opening another conversation also reloads every chat header and every persona's memory. Give the transcript a before-sequence cursor and load older pages on demand. Keep the model's history budget independent from what a user can read. [Room page and refresh](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/platform/storage/RoomStores.kt#L263) · [Page request](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/platform/storage/RoomStores.kt#L304) · [Transcript list](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/ui/chat/ChatScreen.kt#L223)

### P2 · OpenRouter loses actionable errors that ChatGPT already reports

An in-memory endpoint returned HTTP 401, 402, 429 and 503 in separate OpenRouter chat requests. All four returned the same `TextResult.Interrupted`. The UI consequently has no status or reason to distinguish an expired key, a billing problem, rate limiting and a service outage. Preserve a bounded, redacted failure through the existing `ProviderReplyFailure` contract, including failures during catalog lookup. OpenAI-compatible and Ollama chat also discard unsuccessful HTTP statuses. [OpenRouter and compatible chat](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/transport/src/main/kotlin/com/magichandy/mobile/transport/providers/CompatibleProvider.kt#L196) · [Ollama](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/transport/src/main/kotlin/com/magichandy/mobile/transport/providers/OllamaProvider.kt#L89) · [Existing failure UI](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/ui/chat/ProviderFailureText.kt#L12)

### P3 · Explicitly created chats have an empty title in the chat list

The same emulator test exposed a second issue. A chat created automatically by sending a first message got a title. A chat created with **New chat** still had an empty title in the picker after both participants had spoken. The core creates it with an empty string, the append operation only updates activity and speaker, and the picker renders the empty string directly. Use the first user message to title an untitled chat and provide a visible fallback while it is empty. [New chat](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/core/src/main/kotlin/com/magichandy/mobile/core/session/ChatTurns.kt#L70) · [Summary update](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/core/src/main/kotlin/com/magichandy/mobile/core/ports/ChatStore.kt#L13) · [Picker](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/ui/settings/ChatSheets.kt#L233)

## Motion, compatibility and maintainability

- **Handy point density.** I recaptured 210 motion cases. Against the intended sampling policy, **210/210 point counts matched, every authored turn was present, and 208/210 traces matched every timestamp and position**. The two residuals were the same Handy 2 Pro default pattern at 100% on Cloud and Bluetooth, with a maximum interpolated difference of 0.474 percentage points of stroke. Manual and chat captures for an Original Handy at 25% sent 56 points in 12 seconds on both routes. Physical Bluetooth smoothness still needs comparison on hardware. [Shipping policy](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/core/src/main/kotlin/com/magichandy/mobile/core/motion/ScoreTimeline.kt) · [Wire capture](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/transport/src/test/kotlin/com/magichandy/mobile/transport/handy/HandyMotionCaptureTest.kt)
- **Motion-review tooling.** The atlas still compares by transport filename even where Android intentionally uses desktop’s Cloud policy on Bluetooth. This reports only **173/210** exact matches. All **35** additional differences are deliberate Original Handy Bluetooth cases. Some detail plots also label the updated series “Android 0.1.6.” Record the Android version in the capture and display both the actual desktop route and the intended reference policy. [Reference selection](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/tools/motion-review/render.py#L50) · [Plot label](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/tools/motion-review/runtime_plots.py#L181)
- **Install compatibility.** I compared the actual APKs against their GitHub asset digests. The APK went from four native ABIs in v0.1.7 to `arm64-v8a` alone in v0.1.8. The project chose that packaging for voice, and it restricts the **whole APK**, even for people who only type. The main download link still describes compatibility as Android 12 or later. State the 64-bit ARM requirement next to the download. [Release packaging](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/build.gradle.kts#L59) · [Download wording](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/README.md#L5) · [Android ABI guide](https://developer.android.com/ndk/guides/abis)
- **Voice architecture.** The UI imports the platform's `VoiceControls`, `VoiceState`, detector configuration, model-file catalog and `ModelStore`. The 675-line controller owns service lifetime, download recovery, chat buffering and UI state. The architecture test prohibits internal core and transport dependencies but misses this second UI contract. Put the user-facing commands and state behind the additive `core.api` boundary and separate download ownership from voice-turn admission. [UI dependencies](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/main/kotlin/com/magichandy/mobile/ui/voice/VoiceUi.kt#L23) · [Architecture test](https://github.com/MagicHandy/MagicHandy-Mobile/blob/3abba0d1798eaa4f9b96282d3bd6e95622b16456/app/src/test/kotlin/com/magichandy/mobile/architecture/UiBoundaryTest.kt#L15)
- **Phone-only evidence.** The release record distinguishes testing the voice lab on a Pixel 10 Pro XL from testing the shipping feature on an emulator. Full-precision latency, thermals and screen-off battery are still open. The design also requires the phone’s built-in microphone, but the recorder chooses an audio processing source and never checks the actual routed input. Android exposes that route while recording. Include a paired-headset run and inspect the actual route alongside spoken-Stop latency before extending the hardware claim. ## Verification

The checkout matched public `main` and tag `v0.1.8`, four commits after `v0.1.6`. I traced the Stop path through voice, the engine and device transports, and reviewed session recovery, chat and provider admission, persistence, foreground services, UI navigation and release packaging. The clean verification run forced all **182 Gradle tasks** to execute with the build cache disabled. All **1,066 tests** passed (315 core, 248 transport, 503 app), including **106 screenshot comparisons**. Debug and device-test lint reported zero issues. Debug, release and device-test APKs assembled and both minified content checks passed.

Ten additional review probes ran against production classes with simulated peers, synthetic messages, intercepted microphone-service starts and an in-memory database. The chat navigation checks used a disposable emulator in airplane mode with the debug simulator. No physical device, real microphone, private chat or live model account was used. The evidence bundle contains the probes, their exact observations, the motion comparison and the emulator's synthetic UI states. ## Implementation fixes in the 0.1.9 test candidate

The candidate closes the reproducible defects above. The observations in the first half of this document describe v0.1.8.

| Area | Change and verification |
|---|---|
| Stop and microphone consent | A spoken turn carries the original motion epoch and chat ID into the core. The stale “Start motion” regression left the simulated Handy idle and produced zero additional motion batches. Stop during download and retrying a Settings-only download both produced zero microphone-service starts. |
| Model downloads | Cancellation closes the HTTP call. A replacement waits for the previous writer and deletion to finish. Length and SHA-256 are checked on the closed partial file before its atomic rename. The overlapping-writer fixture installed the expected six bytes. |
| Listening and transcribing | Paused motion and held Autopilot now obey the 15-minute quiet timeout. Playing or edging keeps listening active. A bounded queue gives both Stop checks and chat turns time on the recognizer. Ordinary sentences retain their context. Longer turns split near quiet intervals and are submitted once. An overload ends listening with a notice. |
| Microphone routing and architecture | Android checks the actual built-in input before passing samples to speech detection. An external or lost route ends listening. The Compose UI takes its voice controls, configuration and state from `core.api`. Tests enforce this boundary. Model transfers and transcript admission each have their own owner. |
| Handy Bluetooth | Only StopCurrentMode (RPC 715) accepts an ID-only acknowledgment. Setup, append and play require an expected playback-state response for the current stream. Simulated missing and wrong-stream replies to each command left the run idle. |
| Chat and storage | Drafts follow their conversation. A new chat gets a visible placeholder and takes its title from the first user message. Older untitled chats are repaired on reopening. Scrolling back loads indexed pages while keeping headers and persona memory in memory across chat changes. The model's request window stays bounded independently of the visible transcript. The emulator reproduced a clean new composer, the first-message title and restoration of the original draft. |
| Provider failures | OpenRouter chat and catalog lookup, OpenAI-compatible chat and Ollama chat retain actionable HTTP failures. Fixtures cover authentication, billing, rate limiting and service outages using 401, 402, 429 and 503. The UI displays a localized explanation and a numeric status. |
| Motion evidence and compatibility | The atlas records the Android version and reports both the intended sampling policy and the actual desktop route. The two remaining 100% Handy 2 Pro traces differed by at most 0.474 percentage points of stroke, within the existing precise-fit tolerance. The candidate uses up to six seconds for chat and retains the 1.5-second window for Stop detection. The replay used synthetic audio, the production queue and the cross-process link.
