# Handy Cloud and Android integration review

**November 21, 2026 · MagicHandy Test 0.1.5 · Android version code 6**

## Why an online Handy could appear lost

Version 0.1.3 opened a Handy Cloud connection by sending `PUT /hsp/stop`. It accepted only an HSP response reporting stopped playback. A Handy can be online in button mode or idle before a streaming session exists. The vendor also shows an uninitialized playback state in its successful Stop example. Those are different pieces of information. The app could label any of them **Lost**, with the same presentation as an unreachable service. In addition, the cloud setup button labeled **Connect** only saved the row. [Handy API v3](https://www.handyfeeling.com/api/handy-rest/v3/docs/spec.yaml)

The new connection first calls `GET /connected`, then `GET /mode`. Device mode 7 confirms idle. For a known controllable mode, it requests idle with `PUT /mode2`. If the service replies with a generic acknowledgement, the app reads the mode again. Maintenance, firmware updates, and unknown modes do not trigger a mode change. Device setup now attempts the connection after the credential and row have been saved. A failed attempt keeps the row available for retry and displays an explanation. The ordinary connection check only reads reachability. [Cloud handshake](../../transport/src/main/kotlin/com/magichandy/mobile/transport/handy/HandyCloud.kt) · [Setup](../../core/src/main/kotlin/com/magichandy/mobile/core/session/DeviceSetup.kt)

Emergency Stop still goes directly to the priority transport. An HSP Stop response that explicitly says stopped can confirm it. A bare acknowledgement needs independent state evidence. If HSP is uninitialized or reports the wrong mode, the transport establishes device-wide idle. Generic numeric fields, contradictory reports, vendor error envelopes and offline responses cannot confirm a Stop. Start and Resume also request fresh evidence because someone may have used the physical controls since the last run. ## Booting devices and rapid retry

The owner confirmed the repaired handshake connected their real Handy from the emulator in 0.1.4. They then reproduced a separate problem by tapping **Connect** during boot. Android could wait through sequential network operations, and both device screens made the pending attempt impossible to retry. The desktop performs a single connection probe and releases control on failure. Its implementation and the owner's observed timing provided the comparison.

In 0.1.5, a new Handy Cloud connection has one three-second deadline, including foreground-service startup and all of the cloud handshake. An earlier offline response appears immediately. **Retry** on either screen cancels the outstanding attempt and starts a fresh one against the same saved row. The row also offers **Reconnect** as soon as the deadline expires. An already connected device ignores a late Retry tap. The vendor defines a five-second minimum for its server-side timeout parameter, so Android enforces the shorter deadline locally. Existing connected-session checks and emergency Stop retain their separate deadlines. Gemini 4 Neon ran in Antigravity with model `gemini-4-neon-xhigh` and effort `xhigh`. Its first review input was clipped. Three smaller reviews each confirmed they had received the complete input. Their scopes were cloud devices, model providers, and BLE plus Intiface. Only sanitized source went to the reviewer. The initial review session was `c90a2356-a5ed-41e5-8cf1-1256dc146ea6`. The three focused session IDs were `8abb29fc-405e-4e78-b324-b585fd7fd917`, `d20a179d-6f1f-47b8-8492-6a831408567f`, and `71cd3210-d900-43d7-8475-e7c3bb660cfd`. The review archive supplied with the test APK contains their final reports and runtime metadata.

- The reviewer proposed excluding VacuGlide from mixed non-Tempo runs. The port intentionally derives a follower's tempo from the stroke path when another device leads. Tempo-led runs still restrict membership and every command remains subject to the personal and Live limits. [Follower rendering](../../core/src/main/kotlin/com/magichandy/mobile/core/motion/TimedPlayback.kt)
- The reviewer questioned the button-feed timeout and proposed dispatching truncated or data-only events. The vendor specifies a named first event, name-based button events and a heartbeat every 30 seconds. The app keeps its 75-second read deadline and consumes complete named events. [Vendor event contract](https://developers.autoblow.com/reference/http-api-v1-vacuglide/#device-events)
- Existing ChatGPT sign-in already converts provider I/O failures to a network error before the Android storage fallback. Existing recovery Stop already turns transport exceptions into unresolved evidence. The confirmed defects were loss of a rotating credential after a second network dependency and the absence of a store-specific diagnostic when opening a saved device key. ## Verification

The final offline gate passed **936 tests** with zero skips, errors or failures. That comprises 299 core, 229 transport and 408 app tests, including 80 screenshot comparisons. Debug and device-test Android Lint each reported zero issues. Debug, release and device-test assemblies passed, as did both minified package-content checks.

The boot regression held a simulated device silent until the three-second deadline, then connected on the next tap. A second case tapped **Retry** at 200 milliseconds and checked that the previous attempt had been cancelled. A loopback HTTP peer delayed its first connectivity reply while the public form and production transport connected through a fresh request. An explicit offline check then recovered the vendor's error number on the same saved row. The owner's live confirmation covered connecting an online Handy. Boot-time timing and physical Stop on a second phone remain owner acceptance checks.

The non-debuggable test APK supports Android 12 and newer, targets API 36 and passed 16 KiB alignment verification. Its signer certificate matches the previous device-test updates. The 5,014,935-byte APK has SHA-256 `cd322e0fc5d887784c04ec1cdddc64d8a906d1740ef711bc240ddbb5e9d2834c`. [Phone acceptance](../backend/device-checklist.md#verify-handy-cloud-on-a-second-phone)
