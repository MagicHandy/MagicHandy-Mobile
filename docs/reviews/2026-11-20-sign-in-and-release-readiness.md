# Android sign-in and release readiness

## 0.1.3 live chat verification, November 21

After the owner confirmed that the Titan passkey advanced sign-in, MagicHandy 0.1.2 displayed “The model returned an error” on the first chat turn. An owner-authorized text-only test on the Android 17 emulator reached the public Responses endpoint. It returned HTTP 200. OkHttp reported no usable media type, but the body contained standard server-sent events, including text deltas and a completed response. The mobile reader rejected the reply before parsing those events.

Version 0.1.3 checks the event framing when the media type is absent or unhelpful. A reply still requires terminal completion and validation against the requested contract before it is saved or acted on. Provider failures can now carry an actionable category and HTTP status into the chat bubble. Tests cover missing media metadata, refusal, quota errors, incomplete streams and unrelated bodies. ## 0.1.2 phone follow-up, November 21

The phone reached “Return to MagicHandy” in 0.1.1. This establishes that the app received a callback with the expected state. The old connection error covered the subsequent code exchange, signing-key request and local model save, so it cannot identify which operation failed on that phone.

Version 0.1.2 closes the callback listener immediately and waits for the app to resume before sending the grant. Both code exchange and refresh use the documented accounts token endpoint. A connection can recover before transmission, and each grant body is single-use. If an initial exchange fails, an immediate retry can reuse the issued client ID with fresh authorization parameters. The error screen now identifies the failed operation and shows an HTTP status or a recognized connection failure when available. ## What the phone error established

The browser reached OpenAI’s authorization endpoint, which rejected `ext_agent_host_id` before the loopback callback or token exchange. Version 0.1.0 stored and sent the bare string from `UUID.randomUUID()`. OpenAI requires a UUID-based installation ID to use a `urn:uuid:` prefix. The desktop implementation already generated that format. Android now canonicalizes the stored UUID in place before opening the browser. A fresh install creates its own UUIDv4 URN. Reopening the app reuses it. [OpenAI host identifiers](https://developers.openai.com/siwc/token-sharing-open-source) · [Android host storage](../../app/src/main/kotlin/com/magichandy/mobile/platform/storage/ChatGptHostId.kt)

First-time registration uses the dynamic client. Reauthorization uses the issued client and validated identity from that account, including a retained identity-token hint when available. An old credential without the optional hint still works. Matching state, PKCE, signed identity, audience, nonce and an unchanged credential slot protect the exchange. A returning callback may omit its client ID. A mismatched client or subject leaves the previous account intact. ## Independent findings and disposition

| Gemini item | Verification and disposition |
|---|---|
| C1 · Browser authorization and callback lifetime | Fixed the host format and migration, returning client, visible Activity launch, Custom Tab dismissal, shared sign-in deadline and leaving the sign-in screen. A callback must still carry the matching state, even when reporting an error. Accepting an unauthenticated error would allow an unrelated local request to cancel sign-in. Process death abandons that ephemeral attempt and requires starting again. |
| C2 · Stop during task removal or cold startup | Task removal fences output immediately and retains foreground execution while Stop and journal work settle, with an eight-second outer bound. A host loss releases its device connections. Notification Stop retains the broadcast while evidence settles. A cold tile can launch a bounded Stop-only service which grants no motion authority. Cold journal recovery updates the initiating Stop receipt. |
| C3 · Expired device commands | The Android GATT, Autoblow and Intiface drivers distinguish a known denial before submission from a write with unknown delivery. A timed driver resamples a tightened limit on a still-active stream. A partial motor/valve sequence or a write accepted after ownership expired still triggers recovery Stop. |
| H1 · Returning-login UI and unusable credentials | Success follows the saved sign-in event even for an existing connection. A permanently unreadable slot can be repaired by an explicitly verified sign-in. The ciphertext compare-and-set still rejects a late result after removal. A current-token authentication failure marks the saved connection as needing sign-in. Temporary storage failures remain distinct from network failures. |
| H2 · VacuGlide Stop on return | An explicit Stop also targets a detached VacuGlide awaiting return. The separate return obligation ends only after the correlated return-time acknowledgement, or an explicit local check. A timeout or failed retry retains the device row, credential and recovery journal. |
| H3 · Turning motion Off during the first Autopilot plan | Off invalidates planning even before the first motion starts. The planner and motion-admission paths recheck the selected mode after suspension. A late model reply cannot start the device. |
| H4 · BLE priority after Stop | Connection priority is a best-effort power hint. Revoked Bluetooth permission or a retired link cannot turn an already acknowledged Stop into an uncertain one. Actual GATT transport and missing acknowledgements retain their own failure handling. |
| H5 · Loading saved state and opening Live | Production routing waits for the initial Room read before presenting setup or starting an editor. A failed read displays a storage error while keeping Stop accessible. A pending notification navigation request is consumed when Live can actually open. |
| M1 · Setup edits | Saving a model from setup or Chat’s provider chooser selects that exact connection for Chat. Ordinary saves in Models retain the existing selection. Skipping the companion step discards its unsaved edits. Back from adding a device names the correct setup page. |
| M2 · Refusal fallback | The local preview starts with an empty buffer and ignores late data from the previous attempt. Compatible and Ollama clients honor the admitted structured output allowance. The disclosure names the current message, persona wording, and relevant motion and device context. Prior messages and saved memories remain excluded from the fallback request. An explicit request to remember something still follows the person’s memory setting. The initial hosted request already contained that user message. |
| M3 · Persona attribution | Historical replies from before custom personas retain the built-in speaker. Live previews and committed replies both use the persona that began the turn, even if the person switches personas before the reply finishes. |
| M4 · Release contents and distribution | The release checks cover the generated journal, device, model, chat entry and persona vocabulary serializers in the minified DEX. Room exports schema 3. Test-build versions survive diagnostics redaction. Hosted traffic requires TLS and explicitly configured LAN origins keep their private-address checks. Missing saved limits fail closed. Both release scripts exist in the checkout. The reviewer’s source snapshot excluded those tools. The installed Android 17 SDK identifies API 37 as a final platform with preview level zero. Production signing and a published update feed remain owner-controlled. |
