## 2. Release blockers

### P1 · The VacuGlide can exceed the top speed shown on Live

I connected a simulated VacuGlide through the production Autoblow session, lowered Live's top speed from 80% to **20%**, and sent a chat turn proposing a steady 100% tempo. The in-memory vendor peer accepted **100%**. The tempo renderer passes a value up to 100 to the driver, which applies the device's personal range, initially 5–100. Neither step applies Live's ceiling. The checked-in test actually expects 100 at the default 80% ceiling. The UI presents this control as a limit for every source, and the device page shows the personal range as a read-only row. Enforce the intended effective limit at the final motor-write boundary and exercise both an initial request and a lowered limit during playback. [Timed output](../../core/src/main/kotlin/com/magichandy/mobile/core/motion/TimedPlayback.kt#L55) · [Motor mapping](../../transport/src/main/kotlin/com/magichandy/mobile/transport/autoblow/AutoblowSession.kt#L147) · [Existing expectation](../../transport/src/test/kotlin/com/magichandy/mobile/transport/autoblow/VacuGlideSessionTest.kt#L112) · [Device range](../../app/src/main/kotlin/com/magichandy/mobile/ui/devices/DeviceDetailScreen.kt#L325)

### P1 · The app can delete what it needs for a VacuGlide recovery Stop

I ran a saved VacuGlide, removed network validation, and let the peer acknowledge the immediate Stop. The journal correctly retained an obligation to Stop it again on return. While offline, the ordinary Remove form **accepted** deletion of the device. On return, the second Stop was **unconfirmed** and the journal was still armed. Removal uses the engine's confirmed set. Journal cleanup also checks whether a return-time Stop is owed. The production recovery path needs the saved row and its vault handle. Make device removal observe that same outstanding obligation, and keep an explicit local-reconciliation path. [Removal eligibility](../../core/src/main/kotlin/com/magichandy/mobile/core/session/DeviceSetup.kt#L287) · [Durable recovery rule](../../core/src/main/kotlin/com/magichandy/mobile/core/session/RunSafety.kt#L202) · [Detached cloud Stop](../../app/src/main/kotlin/com/magichandy/mobile/platform/PlatformDevices.kt#L239)

### P1 · Losing the foreground service leaves a surviving core able to send motion

Android starts the output jobs in the application scope. Service destruction releases the wake lock, removes the notification and marks the host unavailable. It sends no Stop and gives the running output loop no host-loss signal. A Robolectric teardown confirmed the missing Stop callback. Separately, I withdrew a fake host during a VacuGlide run while keeping the process alive. The simulator accepted **five more motion batches over 8.5 seconds**. Task removal has its own direct Stop, and process death has journal recovery. The surviving-process case needs its own fence before the service gives up ownership. [Service teardown](../../app/src/main/kotlin/com/magichandy/mobile/platform/CoreService.kt#L102) · [Host admission](../../app/src/main/kotlin/com/magichandy/mobile/platform/AndroidHost.kt#L25) · [Continuing playback](../../core/src/main/kotlin/com/magichandy/mobile/core/motion/ManualPlayback.kt#L104) · [Existing lifecycle test](../../app/src/test/kotlin/com/magichandy/mobile/platform/ServiceTest.kt#L64)

### P1 · A fresh Stop receipt can disappear

Two independent paths suppress it.

- **Dismissal survives into a different Stop.** The UI saves a key made from the press count and the IDs of unconfirmed devices. A newly admitted run clears the previous receipt, so its first Stop starts at one again. In a focused test, dismissing one confirmed Stop made a later confirmed Stop with a different timestamp count as already dismissed. Even the onboarding no-device toast goes through the same dismissal callback. Give each Stop episode a stable identity and preserve dismissal only within that episode. [Dismissal key](../../app/src/main/kotlin/com/magichandy/mobile/ui/stop/ReceiptDismissal.kt#L11) · [Receipt reset on admission](../../core/src/main/kotlin/com/magichandy/mobile/core/motion/MotionEngine.kt#L95) · [No-device dismissal](../../app/src/main/kotlin/com/magichandy/mobile/ui/stop/StopReceiptPanel.kt#L62)
- **An old loss banner hides later receipts globally.** I lost a Handy during playback, reconnected it, started a new run and pressed Stop. The core confirmed that Stop while still publishing the earlier loss banner. The root hides every receipt whenever any such banner exists. Only Chat draws the banner, and it lists other devices only when they confirmed. A person on Live can miss a later result entirely. Retire the banner on recovery and associate any duplicate suppression with the particular event and screen. [Global display condition](../../app/src/main/kotlin/com/magichandy/mobile/ui/MagicHandyRoot.kt#L117) · [Loss banner lifetime](../../core/src/main/kotlin/com/magichandy/mobile/core/session/Devices.kt#L196) · [Displayed device outcomes](../../app/src/main/kotlin/com/magichandy/mobile/ui/chat/ChatBanners.kt#L92)

There is a separate durability gap at idle. With an Intiface vibrator connected and no motion run started, an explicit Stop produced a bridge-only, unconfirmed receipt. After simulated process replacement, both the recovery page and the receipt were absent. A journal is created at run admission, so this unresolved explicit Stop had no durable record. The storage design includes unresolved Stops. [Explicit Stop](../../core/src/main/kotlin/com/magichandy/mobile/core/session/RunSafety.kt#L169) · [Journal admission](../../core/src/main/kotlin/com/magichandy/mobile/core/session/RunSafety.kt#L220) · [Storage contract](../../android-architecture-plan.md#L175)

### P1 · The local refusal fallback sends more than the setup screen describes

The approved copy says the app may send “that message, once” to a server on the person's network. With synthetic messages and memory enabled, I observed both a **previous chat turn and a saved memory** in the fallback provider's request. The code reuses the regular conversation window and turn context. A rejected structured answer can also cause a second local request for repair. With fallback Off, a hosted refusal produced a generic interrupted reply instead of the refusal the setting promises. Clearing the fallback invalidates its result, but the in-flight provider call has no cancellation signal from this setting. The picker also classifies a server by provider type. A configured HTTPS server may resolve to a public address and still qualify as local. Define the data, destination and request count covered by consent, then make request construction, cancellation and the UI agree. [Consent copy](../../app/src/main/res/values/strings.xml#L531) · [Fallback request](../../core/src/main/kotlin/com/magichandy/mobile/core/session/ChatProposal.kt#L84) · [Memory and history assembly](../../core/src/main/kotlin/com/magichandy/mobile/core/chat/ChatContract.kt#L252) · [Repair request](../../core/src/main/kotlin/com/magichandy/mobile/core/chat/StructuredTurn.kt#L128) · [Refusal display](../../core/src/main/kotlin/com/magichandy/mobile/core/session/ChatTurns.kt#L247) · [HTTPS address classification](../../transport/src/main/kotlin/com/magichandy/mobile/transport/providers/LocalAddress.kt#L56)

### P1 · Coyote Live reports zero when the device has supplied no measurement

I withheld every B1 strength report during connection and start. Live's state nevertheless showed **A 0 / B 0**. The transport correctly rejected an increase without a baseline. The presentation fabricates a zero when the report is missing, and the feedback collector ignores a later null, which can also leave stale values on screen. Setup submits a zero without waiting for confirmation, so a submitted command is especially poor evidence for a physical reading here. Keep unknown or pending strength explicit and disable the corresponding Live controls until a current report arrives. [Fallback zero](../../core/src/main/kotlin/com/magichandy/mobile/core/session/DevicePlayback.kt#L375) · [Feedback collection](../../core/src/main/kotlin/com/magichandy/mobile/core/session/Devices.kt#L129) · [Zero submission and evidence](../../transport/src/main/kotlin/com/magichandy/mobile/transport/coyote/CoyoteSession.kt#L216) · [Live controls](../../app/src/main/kotlin/com/magichandy/mobile/ui/live/LiveCoyote.kt#L33)

## 4. Chat, Autopilot and phone behavior

- **P2 · A transient planner error can leave Autopilot held indefinitely.** I made only the first planning request fail, then left the provider ready on the same network. Five virtual minutes later the provider had received one call, planning was still Held, and the Bluetooth segment was still playing. A settings, network or user event can wake the planner. The desktop scheduler also has a time-based retry. Preserve the current motion and retry planning within the same eligible run, with bounded backoff or a clear Retry action. All **700** tests passed with zero skips, errors or failures, and Android Lint reported zero issues. The suite comprises 225 core, 122 transport and 353 app tests. The first regression pass should follow a saved device from configuration through an actual driver with a fake peer, then back through the receipt, notification or recovery screen. Start with the VacuGlide ceiling and return-time Stop, service loss, and two consecutive Stop episodes. Those cases cross the boundaries where the existing green checks gave the wrong impression.
